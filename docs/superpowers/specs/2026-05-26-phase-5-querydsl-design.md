# Phase 5 QueryDSL Design

## Goal

Phase 5 compares the existing entity-based product search baseline with a QueryDSL DTO projection implementation under the same request conditions.

This phase is not a k6/Grafana load-test phase by default. The primary evidence is representative SQL, SQL count, integration test output, and short summary documents under `docs/evidence/phase-05/`.

## Scope

Phase 5 focuses on product search and one bulk update comparison.

- Keep the existing product search endpoint as the comparison surface.
- Add a product search strategy parameter so the same endpoint can execute either the baseline path or the QueryDSL path.
- Use `Product` as the main Optimization Target.
- Preserve the baseline implementation intentionally so evidence can compare before/after behavior.
- Keep concurrency control topics such as atomic stock decrement, pessimistic locking, optimistic locking, retry, and idempotency outside Phase 5. Those remain Phase 11 topics.

## Product Search API

The product search endpoint accepts an optional strategy parameter.

```http
GET /api/products?categoryId=1&status=ON_SALE&strategy=baseline
GET /api/products?categoryId=1&status=ON_SALE&strategy=querydsl
GET /api/products?categoryId=1&status=ON_SALE
```

Strategy behavior:

- `baseline`: use the existing Spring Data JPA entity query and map each `Product` to `ProductResponse`.
- `querydsl`: use QueryDSL DTO projection to fetch only fields required by `ProductResponse`.
- omitted strategy: default to `querydsl`.

The API response shape stays `List<ProductResponse>`.

## Product Search Conditions

Phase 5 keeps the user-facing product search condition set small so the strategy comparison remains direct:

- `categoryId`
- `status`

Both strategies support these same conditions. `categoryId` and `status` may be omitted independently, and the QueryDSL path must exclude omitted conditions from the generated predicate.

Additional search dimensions such as `minPrice`, `maxPrice`, and `keyword` are outside this Phase 5 design.

## Service Shape

Introduce an enum for explicit comparison.

```java
public enum ProductSearchStrategy {
    BASELINE,
    QUERYDSL
}
```

`ProductService.searchProducts(...)` routes by strategy:

- `BASELINE` delegates to the existing repository method.
- `QUERYDSL` delegates to a QueryDSL repository/custom repository method.

The strategy branch exists because this repository is an Ecommerce DB Optimization Lab. In a production ecommerce API, this comparison strategy would usually not be exposed as a user-facing parameter.

## QueryDSL Repository

Add a QueryDSL-backed product search component with a focused responsibility:

- Build predicates from optional `categoryId` and `status` conditions.
- Select only `ProductResponse` fields.
- Return the same response data as the baseline path when equivalent conditions are used.

The repository should use the QueryDSL Q-types generated by the existing Gradle annotation processor setup.

## Bulk Update Experiment

Phase 5 also includes a small bulk update comparison for `Orders`.

- Baseline: load `Orders` rows by status and update each row through dirty checking.
- Query path: execute one JPQL bulk update from old status to new status.
- Evidence compares SQL count and documents persistence context stale state risk.

This experiment does not solve stock, coupon, or order concurrency control. It only demonstrates row-by-row update vs bulk update behavior and the need to clear or avoid stale persistence context state.

## Testing

Use integration tests or focused repository/service tests against PostgreSQL/Testcontainers where possible.

Tests should verify:

- `baseline` and `querydsl` strategies return the same `ProductResponse` values for the shared condition set.
- omitted strategy defaults to QueryDSL.
- QueryDSL `categoryId` and `status` conditions are omitted when null.
- invalid strategy input is rejected or mapped by the existing Spring enum binding behavior.
- bulk update changes the expected rows.
- persistence context behavior after bulk update is either cleared automatically or documented by a test.

## Decisions

- The final URL parameter name is `strategy`.
- The supported strategy values are `baseline` and `querydsl`.
- The default strategy is `querydsl`.
- k6/Grafana are optional, not required, for Phase 5.
